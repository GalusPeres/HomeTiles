# Contributing to HomeTiles

Start with [ARCHITECTURE.md](ARCHITECTURE.md) for subsystem ownership, data
flow, known limitations and the next useful refactorings. Device-specific
facts live in [BOARD_SETTINGS.md](BOARD_SETTINGS.md) and the device READMEs.
[AGENTS.md](AGENTS.md) is the repository's agent rulebook;
[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) records current shared state.

## Find the owning module

| Change | Start here |
| --- | --- |
| Board wiring, panel initialization, touch or storage hardware | `src/devices/<exact-device>/` |
| Shared hardware facade, display buffers, power, crash reports or firmware update | The matching `src/core/hardware/`, `display/`, `power/`, `diagnostics/` or `firmware/` module |
| Build/release/installer identity | `tools/device-profiles.json` and `sketch.yaml` |
| Tile rendering, HTTP fields and translations exported to the browser | `src/types/<type>/` |
| Runtime state, widget records and type-specific inline helpers | The type's `state.h` or `widgets.h`; `src/tiles/runtime/tile_renderer.h` remains the compatibility entry point |
| Stable tile IDs and shared eligibility rules | `src/types/tile_type.h`, `src/types/tile_type_policy.h` |
| Active/sleep queue service order and budgets | `src/tiles/runtime/tile_update_service.h` |
| Folder snapshots and cached state application | `src/ui/tabs/tiles/tab_tiles_unified.cpp` |
| Tile records, migration, sidecars and filesystem recovery | `src/tiles/config/tile_config.cpp` |
| Settings persistence and its parental-control record format | `src/core/config/` |
| MQTT parsing/commands, Bridge metadata or transport backends | `src/network/mqtt/`, `src/network/bridge/` or `src/network/transport/`; `network_manager.*` coordinates them |
| Popup controls and shared popup geometry | `src/ui/popups/<type>/` and `src/ui/popups/popup_layout.h` |
| Settings tabs, screensaver, boot UI or shared UI components | `src/ui/tabs/`, `src/ui/screensaver/`, `src/ui/startup/` or `src/ui/shared/` |
| Shared browser editor behavior | `src/web/admin/` |
| Type-specific browser behavior | `src/types/<type>/admin*.js` |
| HTTP endpoint behavior | `src/web/server/handlers/`; lifecycle/routes stay in `src/web/server/web_admin.cpp` |
| Server-rendered pages, embedded resources or initial setup | `src/web/server/render/`, `src/web/server/assets/` or `src/web/setup/` |
| Localized UI text | `src/core/i18n/i18n.h` and `i18n.cpp` |
| Regression tests | `tools/tests/<area>/test-<topic>.mjs`; shared harnesses and fixtures remain in `tools/lib/` and `tools/fixtures/` |
| Firmware release procedure | [RELEASING.md](RELEASING.md) |

Generated assets, fonts, icons and vendor firmware can be large without
being maintenance problems. Change their source or generator instead of
manually editing generated bytes. Preserve upstream attribution and exact
board revisions when updating vendor code.

Choose folders by responsibility, using the same structure across core, network,
UI, tiles and web code. Keep matching headers and implementations together and
extend an existing owner before introducing a generic helper directory. Folder
placement does not change thread ownership, initialization order or hardware
support. The architecture map explains those boundaries.

## Browser source workflow

`src/web/assets/admin.js` is now an assembled artifact. Edit the owning
source unit listed in `src/web/admin/bundle.json`. Install Node.js/npm on the
build computer, then run these commands from the repository root. Repeat the
dependency installation after checkout or a lockfile change, before host tests
or asset generation:

```text
npm ci --ignore-scripts
node tools/generate-web-assets.mjs
node --check src/web/assets/admin.js
node tools/generate-web-assets.mjs --check
node tools/run-tests.mjs
```

The assembly preserves a single classic script, its existing global names,
initialization order and one compressed HTTP asset. It introduces no module
loader, extra requests or runtime registry. Individual source units must
contain complete declarations. A new browser source file must be listed
once in the bundle manifest; missing, duplicate and invalid entries fail
validation. Unchanged generation preserves file timestamps and compiler
caches.

The readable assembly stays intact. Firmware delivery uses pinned Terser 5.51.2
with `compress: false` and `mangle: false`, followed by gzip. An independent
Acorn syntax-tree check permits only lexical metadata differences and equivalent
ordinary data-property shorthand; other differences fail generation. The tools
are host dependencies only. Check generated output and measure final BINs;
readable and delivered JavaScript deliberately have different bytes.

This is source modularity, not complete JavaScript scope isolation. Shared
editor state still has a single owner in `tiles/state.js`; type modules use
the existing registry callbacks and common editor helpers. Avoid introducing
additional globals when a type callback or existing state owner is enough.

## Add an exact device profile

1. Establish the exact board revision from primary hardware documentation.
   Add its driver/profile beneath `src/devices/<device>/` and record tested
   hardware facts in its README. Keep GPIOs, timings, reset sequencing and
   transport workarounds with that exact device.
2. Add the exact pinned Arduino profile to `sketch.yaml`. Add its matching
   entry to `tools/device-profiles.json`, including build profile, firmware
   metadata key, release key, define, chip family, flash size, silicon range,
   transport variant and installer presentation.
3. Connect firmware selection through `src/devices/device_select.h`,
   `src/devices/active_device.h`, `src/core/firmware/firmware_metadata.cpp` and
   the setup AP name in `src/web/setup/web_config.cpp`. Preserve
   the existing manual default. Similar product names do not prove shared
   hardware behavior.
4. Run `node tools/generate-device-profiles.mjs`. The local builder, importer
   and packager consume the catalog; the browser profiles and CI matrix are
   generated from it. Do not maintain new independent maps in those tools.
5. Add focused profile assertions and update support/availability docs.
   Build the exact profile and inspect both OTA and factory identities.
   Record actual hardware results separately from compilation.

Build names, release keys and firmware metadata keys are intentionally
different concepts. Waveshare 7B v3.1 shares its firmware key and define
with pre-v3 7B, but has a different release key, profile and silicon contract.
Layout-test profiles are local-only. The catalog validates these distinctions
and the tests retain readable compatibility fixtures for existing profiles.

## Add a tile type

Use a mature type with the closest behavior as the reference. The registry
already connects rendering, request application and browser form callbacks;
the policy header centralizes cross-cutting eligibility. These are separate
responsibilities.

1. Append an unused stable ID in `src/types/tile_type.h`; never reuse a retired ID.
   Define the intended persistence, cached state, popup, MQTT and screensaver
   policies in `tile_type_policy.h`. These policies deliberately have
   different memberships: an entity field alone does not imply all features.
2. Implement the type module and add its descriptor to `types_registry.cpp`.
   Add its UI strings centrally for every registered language and export
   type-specific translations through its `web_scripts.cpp`. Write source
   comments and diagnostic logs in English.
3. Put browser field/preview logic beside the type and list it in the bundle
   manifest. Use the registry load/save/reset callbacks and existing shared
   draft/autosave helpers. Check both selected and cached-grid previews.
4. Define every saved field's reset, validation, copy/import/export and
   migration semantics. `PackedTileV7` remains a binary contract; a new field
   requires explicit design for its storage and any sidecar lifecycle.
5. Put bounded runtime state and widget records in the type's own header,
   with a clear reset owner and explicit header dependencies. Register
   queue service in `tile_update_service.h`; connect state dispatch and cached
   restoration with the same semantics. Keep LVGL work on its existing owner.
6. Check folders, unavailable states, repeated popup open/close, sleep/wake,
   save/reload/reboot, copy/paste and import/export. Home Assistant Bridge is
   a separate repository and needs its own compatible integration work.

New type work still involves runtime routing and persistence review; the
refactoring does not make a rendered tile automatically complete. The full
contract and hardware-specific lifecycle checks remain in `AGENTS.md`.

## Add a language

A language is data only: one `Strings` table and one `LocaleProfile` table
in `src/core/i18n/i18n.cpp`. The panel, its keyboard and the Web Admin take
everything from them; no renderer, keyboard or browser code changes.

1. Start from the English tables `kStringsEn` and `kLocaleEn` and name the
   copies after the language code, for example `kStringsIt` and `kLocaleIt`
   for `it`. Both tables are positional: translate every entry in the field
   order of `struct Strings` and `struct LocaleProfile` in
   `src/core/i18n/i18n.h`, and leave none out. Put the code in `code` of
   both tables and in `html_lang`.
2. Register the pair in `kLanguages`. Its order is the order of the language
   list on the panel and in the Web Admin; the first entry, English, is the
   fallback for an unknown code.
3. Fill in the `LocaleProfile` data the language brings:
   - `native_name` for the language list and the `decimal_separator`.
   - Dates: `short_date_pattern` (`{d}` day, `{m}` short month),
     `long_date_pattern` and `long_date_year_pattern` (`{d}` day, `{M}`
     month, `{Y}` year, for example `"{d} de {M} de {Y}"`),
     `month_names_in_date` as the months stand in a date (the genitive in
     Polish, Czech and Slovak), the short month names
     `weather_months_short`, and the weekday names `weekday_names` and
     `weather_weekdays_short`, Sunday first.
   - `default_time_format` (1 = 24-hour, 2 = 12-hour) and
     `default_date_format` (1 = day/month/year, 2 = month/day/year,
     3 = year/month/day) for **Auto**.
   - The time zone names `timezone_group_labels` and `timezone_labels`, in
     the order of `i18n::timezone_option()`.
   - `keyboard_layout` under **Auto** (0 QWERTY, 1 QWERTZ, 2 AZERTY) and
     `keyboard_letters`, the language's own letters and signs in lower case,
     for example `"áčďéěíňóřšťúůýž"` for Czech.
     `src/ui/tabs/settings/keyboard_letters.h` makes the capitals, the
     accent page and the forms of a held letter from them; English leaves
     the string empty.
4. Use only characters the panel fonts carry: Latin-1, Latin Extended-A,
   general punctuation and the euro sign. Any other character, for example
   the minus sign U+2212, shows as nothing on the panel.
5. Keep printf placeholders (`%s`, `%u`, `%d`), named placeholders such as
   `{n}`, `{name}` or `{query}`, `**bold**` markers and `\n` line breaks
   exactly as in English.
6. Name the new language in the language list and the keyboard paragraph of
   "Localization" in `docs/device-ui.md`.

The i18n tests find every registered language by themselves: complete,
aligned tables, the same printf placeholders as English, only characters of
the panel fonts, keyboard letters that lead the accent page and fit its
rows, and the same clock dates on the panel and in the Web Admin preview.
A few tests also list known texts per language and need the new language's
expected texts: `tools/tests/ui/test-settings-display-page.mjs`,
`tools/tests/ui/test-settings-localization-page.mjs`,
`tools/tests/web/test-local-camera-rotation.mjs`, and the month format
patterns in `tools/tests/tiles/test-clock-date-options.mjs`. Install the
host dependencies once after checkout, then run the language tests and the
whole suite:

```text
npm ci --ignore-scripts
node tools/run-tests.mjs i18n keyboard clock-date
node tools/run-tests.mjs
```

Long texts can be cut on the 480 px panels. `node tools/settings-preview.mjs
s3 --page=system --lang=it --no-mockup` renders a Settings page in that
language with the panel fonts into `build/settings-preview/` (it needs
LVGL 9.6 and a host compiler); `--page` also takes `display`, `wifi`,
`localization` and `setup`.

## Verification and firmware size

### Documentation

The documentation source is `docs/`, `mkdocs.yml`, and `overrides/`. Keep the
README as a short introduction linking to https://galusperes.github.io/.
Installation belongs on `docs/installer.md`; manual flashing is a short
alternative on that page. Device status and issue links belong in the Overview
device list, rather than repeated hardware tables throughout the guides.

Build with `python -m mkdocs build --strict`. The docs workflow tests the
installer, mirrors published release assets, checks links and SHA-256 digests,
then publishes a `gh-pages` snapshot. The `GalusPeres/galusperes.github.io`
repository deploys that snapshot at the root URL, checking for changes twice
per hour. For immediate publication, run its **Publish HomeTiles documentation**
workflow and verify the live site. Keep firmware assets on the same origin as
the online flasher.

### Firmware verification

After installing host dependencies as above, the normal verification entry
points are:

```text
node tools/generate-device-profiles.mjs --check
node tools/generate-web-assets.mjs --check
node tools/run-tests.mjs
python -m mkdocs build --strict --site-dir build/docs
git diff --check
```

The suite recursively discovers `tools/tests/<area>/test-*.mjs`. Use the existing
`build`, `core`, `devices`, `network`, `tiles` or `web` area; CI uses the same
runner, so a new test needs no manually maintained workflow entry. Run a subset
with a path/name fragment, for example `node tools/run-tests.mjs network/ i18n`.
Host C++ tests use the production policy/codec/service code with minimal
platform shims. Browser tests execute production JavaScript paths. A test that
reports `SKIP:` has not verified that behavior; install its optional tooling
before relying on that coverage.

The maintainer's two refactoring test profiles are `waveshare_8` and
`guition_esp32_4848s040`:

```powershell
./tools/build-firmware-local.ps1 -Profile waveshare_8 -OutputDirectory build/candidate/waveshare_8
./tools/build-firmware-local.ps1 -Profile guition_esp32_4848s040 -OutputDirectory build/candidate/guition_esp32_4848s040
```

Use normal incremental builds. Build sequentially: the helper temporarily
hides `sketch.yaml` and selects the appropriate ESP-Hosted toolchain object.
For before/after comparisons, use the same checkout path, toolchain, library
versions and build flags, with separate baseline/candidate output directories.
Keep the reference outputs; copying an old release is not an equivalent
baseline for a different source revision or toolchain.

```text
node tools/compare-firmware-size.mjs --baseline build/baseline --candidate build/candidate --profile waveshare_8 --profile guition_esp32_4848s040 --report build/firmware-size.json
```

This checks actual application BIN lengths and board/silicon metadata,
records absolute paths and SHA256 hashes, and fails on any growth. Factory
images are padded to flash size and cannot reveal application size growth.
Use existing diagnostic logs and the hardware matrix in the architecture
guide to evaluate loop latency, heap headroom, touch responsiveness, camera
behavior and repeated storage/OTA operations. Compilation is not a runtime
or hardware benchmark.

Keep commits focused and explain the concrete behavior, compatibility and
verification. A local refactoring build is not a firmware release; published
versions and release assets follow `RELEASING.md`.
